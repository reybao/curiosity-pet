# Stage 1: command-line voice loop

## Implementation

- `uv run pet`: microphone + VAD (ends automatically when speech stops); `--ptt` hold-to-talk fallback; `--wav` recorded file; `--text` typing; `--no-play` no playback.
- Flow: Silero VAD (0.8 s) -> Qwen3-ASR-0.6B 4-bit -> language detection -> pet-chat streamed generation -> Kokoro v1.1-zh per sentence -> background playback.
  As soon as VAD decides speech has ended, a local cue sound plays. Session history lives only in memory and is cleared at the end.
- Kokoro v1.1-zh: the official repository has only PyTorch weights, which `scripts/convert_kokoro.py` converts locally to safetensors (`~/pet-models/kokoro-v1.1-zh`, not committed).
  Chinese uses the misaki 1.1 G2P, with Chinese voice zf_001 and English voice af_maple.
- No network at runtime: `HF_HUB_OFFLINE=1`; misaki used to download a spaCy English model at runtime, and it is now installed as a pinned project dependency.
- Goodbyes ("再见", "bye") get a fixed closing line without calling the model.
- When the local model is unavailable, it reads aloud "我现在有点累,等一下再问我吧" ("I'm a bit tired, ask me again in a little while") and does not switch to an external service (tested).
- Pipecat is not used in this stage: a single process chains everything directly, and the modules (vad/asr/llm/tts/audio) stay independent; whether to use Pipecat to carry transport is decided in Stage 2 when connecting the iPad.

## Findings during tuning

1. **TTS and generation fight over the GPU**: Kokoro alone synthesizes 4.8 s of audio in 0.38 s, but 1.13 s while generation runs at the same time (about 3x). On CPU it takes 37 s, which is not feasible.
   So the first chunk was shortened: once the first chunk has 8 characters it may break at a comma; in English once the first chunk has 8 words it may break before a conjunction (when, because, and, etc.).
   Later sentences still split at periods as usual, and synthesis (about 4x real time) is faster than playback. Before optimization the median time to speak was 3.12 to 3.37 s, with only 5/16 runs meeting the target.
2. **Full-width punctuation missed**: the full-width `!?;,` in the sentence splitter had been written as half-width, so Chinese split only at periods. Changed to the escaped form and added tests.
3. **Chinese words inside English answers** were read by the English G2P as "Chinese letter". Chinese-character fragments in English answers are now synthesized with the Chinese voice;
   Kokoro adds silence at the start and end of each segment, which is trimmed before joining, otherwise pauses exceed 0.8 s (which in measurement made the VAD cut a sentence off).
4. **Ollama memory keeps growing** (unresolved, see below).

# Stage 2: iPad web access (in progress)

## Implementation

- `uv run pet-server`: a single FastAPI process listening only on `127.0.0.1:8730`; loads and warms up ASR and TTS (Chinese and English pipelines) at startup.
- The voice channel uses a FastAPI WebSocket, not Pipecat (reasons in DECISIONS.md). The iPad sends 16kHz PCM16, and the server does VAD, recognition, generation and synthesis,
  sending text and 24kHz audio back sentence by sentence; the iPad plays it and highlights the current sentence. Half duplex: audio received while the pet is thinking or speaking is dropped.
- The pet: an SVG + CSS little robot with four states (listening, thinking, speaking, plus idle breathing and blinking). Only system fonts, and the page references no external address (tested).
- iPad side: an AudioWorklet downsamples the microphone to 16kHz; when VAD decides speech has ended, the iPad plays a cue sound locally; "hold to talk" fallback; "end" clears the session history.
  Adding `?text=1` to the address shows a typing box, handy for debugging without a microphone.
- Access restrictions: the service listens only on the local machine; it also validates Host (accepts only 127.0.0.1, localhost, `*.ts.net`, to prevent DNS rebinding) and the WebSocket Origin.
- The child's words are not logged: the service log writes only timing and language, not questions or answers (tested; the log was also checked and has none).
- Browser check (Browser pane, typing mode): switching among the four states, sentence-by-sentence highlight, returning to listening after playback, and stopping playback when "end" is pressed midway all work, with no console errors.

Tests: `uv run pytest` 59 all pass (14 new server tests, using fake ASR, TTS and VAD).

## Finding: Ollama + Qwen3.5 cannot reuse the prompt cache

In web sessions with history, the first token rose from about 0.2 to 0.8 s to 1.5 to 1.7 s. Ollama log:
`forcing full prompt re-processing due to lack of cache data (likely due to SWA or hybrid/recurrent memory)`.
Qwen3.5 is a hybrid architecture (with recurrent layers), so llama.cpp needs context checkpoints and a memory cache to reuse the prefix, but Ollama always passes
`--cache-ram 0` when it starts llama-server; the environment variables `LLAMA_ARG_CTX_CHECKPOINTS` and `LLAMA_ARG_CACHE_RAM` cannot override it either (in testing, all 8 requests were forced to recompute).
So every turn prefills the system prompt and history from scratch, at about 370 tokens per second. The MLX-engine build is fast and its memory keeps growing precisely because it retains the prompt cache.

Mitigation (no component change): shorten the system prompt (Chinese 193 characters); the session history carries only the last 2 turns, with older answers truncated to 120 characters.
First token over 5 turns of one session: before, 0.71 -> 1.42 s and still growing; after, 0.53 -> 0.87 s and capped (prompt about 310 tokens).
Language-following retest is still 36/36.

# Stage 4 (in progress): Wikipedia lookup and privacy gate (2026-10-24)

The parent confirmed: general-knowledge questions with no local material may go online; personal and family information and mood are never sent out. For now the only source is Wikipedia.
A narrow exception was added to hard constraint 1 in CLAUDE.md, with a new "Online lookup" section; DECISIONS.md records the reasons.

## Implementation

- `privacy.py`: coarse screen (does it look like a knowledge question; anything with "I", family, emotion or secrets goes offline directly, without calling the model),
  a sensitive-topic check on the original words, and a search-term rule check (first person, family and parent-configured names, school, address, digit strings, contact info, emotion, secrets, sensitive topics, blocklist, length).
- `lookup.py`: the local model classifies and rewrites into a topic term using JSON Schema (temperature 0), then the rule check runs; only after passing is Wikipedia queried.
- `wiki.py`: connects only to the three Wikipedia domains zh / simple / en; the only free text in a request is the search term; no cookies; failures return empty and do not affect the answer.
- Answer flow: when going online, first say "我去查一查!" ("let me look it up!"); the first 450 characters of what is found go into this turn's prompt (not into history), the answer cites the source, and the page shows "Source".
- `store.py` (`PET_DATA_DIR/pet.db`): search terms are deleted after 7 days, with per-week per-topic counts kept long term (for factual trends in the weekly report); retrieved material is stored as pending review.
- The service log records only whether it went online and why, not questions, search terms or answers.

## Unresolved: Wikipedia requires contact information

The Wikimedia User-Agent policy requires automated programs to include contact information, and requests without it are blocked (403 in testing; swapping to compressed headers can bypass it, but that would evade their bot detection, so we do not do it).
The contact is now a config item `PET_WIKI_CONTACT`; if unset, it does not go online. Waiting for the parent to provide one (a dedicated mailbox is suggested).

## 9B in real use: reverted (2026-10-24)

The parent chose to try the 9B for a week, accepting about 0.6 s more. In the live server the cost was much larger
than the isolated numbers suggested, because every lookup turn calls the model twice (classify-and-rewrite, then
the answer with a reference) and both halves are slower on the 9B:

| Setup | Plain turn, first audio | Lookup turn, first audio (filler) / first token |
|---|---|---|
| 4B alone | about 1.0 s | about 1.8 s / 2.5 s |
| 9B alone (also as helper) | 3.5 s | 2.4 to 2.6 s / 3.7 to 5.7 s |
| 9B main + 4B helper, both loaded | 2.4 s | 11 to 15 s (swap 11.6 GB; the machine thrashed) |

Two models do not fit next to the speech models in 16 GB. The 9B alone pushes lookup turns to 4 to 6 s before
the first real sentence. Reverted to the 4B; the 9B stays available (`"chat_model": "pet-chat-9b"`). A later option
is a rule-based rewriter (no model call) so that the 9B would only pay for the answer; it would need its own
privacy evaluation.

Also added this round: date and time questions are answered from the Mac's clock (the model said "Wednesday"
on a Saturday), and a date note is added to the prompt whenever the question mentions days or dates.
